## 一、结构与规模

**1. 过长函数（Long Function）**——一个函数从头干到尾，读者跟到后半段，前半段设的前提已经记不牢。
- 表现：给它起名时一个动词不够用、总想再添一个才说得全；校验细节与业务步骤搅在同一层；一个临时变量从函数头活到函数尾，中间还隔着互不相干的段落。检测：统计非空非注释行数（阈值依项目规模档案在 20–100 行间取值）；留意为同一变量赋值的两个段落相距上百行的形态。修法：以阶段为边界抽取子函数（Extract Function），父函数只留一份单一抽象层的流程提纲。

**2. 过大文件（Large File）**——单个文件胖到难以定位、难以通读，也说不清归谁管。
- 表现：动一行就引发整段重写，最终落进「模型修不动、人不敢拆」的僵局；三类不计入：机器产出的产物文件、纯数据罗列的表、原样搬进仓库的第三方代码。检测：行数越过规模档案档位（200–1000 行）；import 自四面八方汇入同一文件。修法：沿职责缝切成模块；动手前先用特征测试把既有行为钉住。

**3. 过深嵌套（Deep Nesting）**——控制结构层层堆叠，主路径被缩进淹没。
- 表现：4 层以上 if/for/try 嵌套；正常逻辑沉在 else 里。检测：数峰值缩进深度；grep 深缩进区域（如 `^\s{16,}`）。修法：用卫语句与早返回拍平，把失败路径赶到函数开头。
```python
if post and post.draft and post.author.active:
    if post.approved:            # 坏：主路径埋进两层嵌套
        db.save(post)
if not post or not post.draft or not post.author.active:
    return                       # 好：卫语句提前退出，正文只剩一行
```

**4. 上帝类（God Class）**——一个类型囤积多个互不相关的变更理由。
- 表现：几十个 public 方法服务完全不同的调用方；字段甲只有方法组 A 用，字段乙只有方法组 B 用。检测：列出每个方法触达的字段集合，集合几乎不相交即职责分裂。修法：按字段-方法聚类拆类（Extract Class），搬走行为而不是再造数据袋。

**5. 补丁堆积（Patch Accumulation）**——函数长高靠一轮轮追加特判，而非围绕真实规则重新组织。
- 表现：`if vip_flag`、`if old_route` 式的条件一票一票垒起来占了函数大半；注释里留着「某年大促临时加的」这类时间戳痕迹。检测：搜条件里的形容词式开关（vip/old/temp/hack）；看各分支能否拼出一张公共表。修法：把特判压成数据表或规则集，入口处一次分派。
```python
if zone == "cn": fee = 8
elif zone == "far": fee = 25      # 坏：每开一个新区域就多一层判断
FEE = {"cn": 8, "far": 25}        # 好：运费入表，新区域只添一行数据
```

**6. 过长参数列表与数据泥团（Long Parameter List / Data Clumps）**——调用方被迫传一串散装实参；同一小组值总在多个签名里结伴出现。
- 表现：同名三参数组合跨函数复现；布尔旗标参数控制函数走哪条分支。检测：数声明参数（4 个以上警觉）；grep 重复出现的参数名组合。修法：结伴值组团为参数对象（Introduce Parameter Object）；旗标参数拆成两个意图明确的函数。

**7. 变更轴错位（Divergent Change / Shotgun Surgery）**——一个模块因多种不相关理由被改（发散），或一个概念变更被散射到多个文件（霰弹）。
- 表现：git 历史里同一文件交替承接持久化、UI、计费改动；一个字段改名牵动十个文件。检测：看提交历史的重复并行编辑；同一概念的修改若总得成串落在多个文件，即是信号。修法：发散则按变更理由拆模块；霰弹则把该概念聚拢到单一归属地。

## 二、防御与错误处理

**8. 吞错（Swallowed Exception）**——异常被捕获后不上抛、不恢复、不产生任何可见失败。
- 表现：空 catch；`except: pass`；catch 后只 console.error 就继续；Promise 链缺 `.catch()`。检测：grep `except: pass`、`catch (e) {}`、`console.error` 后无 return/throw；支付、计费、数据写入路径逐个查。修法：能恢复就恢复并记录，不能恢复就快速失败上抛；高危路径禁止静默续行。
```python
try:
    charge(user, amount)
except Exception:
    pass            # 坏：扣款失败被当成功，下游照发订阅
```

**9. 含糊报错（Vague Error）**——抛出的错误不携带定位问题所需的信息。
- 表现：`throw new Error("Something went wrong")`；裸字符串异常；重新包装时丢掉原始错误链。检测：grep "Something went wrong"、"failed"、无参数的 `Error(`/`Exception(`。修法：错误信息带上操作、关键参数快照与原因链（cause），让读者不开调试器就知道哪一步坏了。

**10. 错误路径缺口（Missing Error Paths）**——只写了 happy path，被调用方失败时的行为无人定义：该防不防。
- 表现：外部调用（HTTP/DB/文件）无超时无失败分支；可空返回值不检查；后台任务失败即无声停止。检测：对每个外部调用问「它抛错或返回空时，接下来会发生什么」，把错误的下落追到底——是消失无痕、进了日志、换了件外衣，还是原样传了出去。修法：为每类失败写显式分支；后台任务失败必须可见（重试、告警或状态标记）。

**11. 失败读成成功（Failure Read as Success）**——失败被折算成正常值域内的空结果，上游无从察觉。
- 表现：catch 后返回 `[]`/`null`/`0`；跳过部分记录仍宣称迁移完成；管道上一环节退出码没读就继续 commit。检测：查所有 catch 块的返回值是否落在「正常值域」里；确认退出码被读取而非只看有无输出。修法：失败以可区分的状态冒泡（错误或部分结果计数），禁止用正常空值顶替失败。
```python
try:
    rows = db.export_users()
except ExportError:
    return []      # 坏：导出失败被折算成「没有数据」，报表照常出
```

**12. 假设性加固（Hypothetical Hardening）**——没有落地用途的「以防万一」机制：不该防乱防。
- 表现：没有任何流程消费的校验和；为想象调用方预留的兼容层；从未改变过行为的开关。检测：对每个防御问两个问题——它检测到问题后导向什么动作、谁消费这个信号；无消费者即删除候选。修法：删掉无消费者的防御；有真实流程接住的保留（判据是用途，不是机制的名字或行数）。

**13. 可定义掉的错误（Definable Error）**——本可通过重定义语义消除的条件却抛异常，异常分支比主逻辑还厚。
- 表现：`unset(x)` 在 x 本就不存在时抛错；防御分支极少被测试执行，成为藏 bug 的暗区。检测：找「仅因调用顺序假设而抛异常」的分支；比较 try 块与主逻辑的行数比。修法：改语义让非法状态不可表达；消除不了的错误就地低层处理；不可恢复的直接崩溃，别包装。

## 三、抽象与分层

**14. 投机泛化（Speculative Generality）**——为想象中的未来搭建的抽象、参数与扩展点，当下无人使用。
- 表现：单实现接口配工厂加策略三件套；从未使用的类型参数；只有一条路径的 hook；标准库或既有轻量依赖已够用，却整包引入一个大库。检测：数每个抽象点的真实实现数（1 个即嫌疑）；自问「删掉这层，调用方到底损失什么」。修法：内联（Inline）掉单实现层；按「同一知识三次真实重复才抽象」的纪律重建。

**15. 过度分层（Over-Layering）**——controller→service→serviceImpl→manager→helper 式层层转发，每层只给下一层换了个名字。
- 表现：Impl/Manager/Helper/Util 后缀成串；业务规则一行没写先铺满五层骨架；把「文件变多」当成模块化成果。检测：grep 文件名中的 `Impl|Manager|Helper|Util`；追一个请求的调用链，数「只转发不添加信息」的层数。修法：每层必须提供不同抽象，只转发的层合并掉——碎片化不等于模块化。
```python
router.post("/orders", ctrl.create)   # 只做参数校验和转发
  -> orderService.create(...)         # 只做转发
     -> repo.insert(order)            # 真正写库——三层留两层就够
```

**16. 直通方法（Pass-Through Method）**——方法体只是把大部分参数原样转发给另一个对象的同名方法。
- 表现：`self.inner.foo(a, b, c)` 式一行方法成排；接口随被委托对象同步膨胀。检测：找方法体只含单个委托调用的函数；同名方法沿调用链重复出现。修法：让调用方直接持有被委托对象（移除中间人），或让这一层承担真实的差异职责。

**17. 贫血实体（Anemic Model）**——类型退化成字段袋，业务规则全部外溢到 service，封装归零。
- 表现：实体只有 public setter；同一不变量校验在每个调用点各写一份。检测：找「只有字段加 getter/setter、无任何行为」的类；看不变量是否只能到 service 里才拼得出来。修法：把规则搬回拥有数据的方法（Move Function），让非法状态在构造处就被拒绝。

**18. 依恋外家数据（Feature Envy）**——函数频繁伸手取别的类型的数据，对自己的状态反而冷淡。
- 表现：一个方法大半篇幅在读另一个对象的字段与调用其 getter。检测：数外部对象访问次数与自身状态访问次数的比值。修法：把函数搬进它羡慕的类型；确属多对象协作则提炼出中立对象承接。

**19. 消息链（Message Chains）**——调用点串起一长串中间对象，调用方对对象图知道得太多。
- 表现：`a.b().c().d()` 式链式取值；链上任何一环换实现都会断。检测：grep `)\.\w+\(` 连点模式；例外：fluent DSL 与测试构造器不算。修法：用 Hide Delegate 收敛为一个语义化入口方法。

**20. 配置外推（Config Extrusion）**——该内部拍板的决策被导出成参数，复杂度转嫁给调用方。
- 表现：函数带 retries/timeout/strategy 等一排开放参数且无默认约定；文档教用户「按需调整」。检测：对每个参数问「调用方真能选出比实现方更好的值吗」。修法：收编为内部决策；确需暴露时给安全默认值，别让调用方替你做设计。

## 四、数据与状态

**21. 基本类型偏执（Primitive Obsession）**——领域概念用裸 string/number/bool 携带，校验与格式化规则散落各处。
- 表现：user_id/status/金额到处以裸字符串流动；同一 email 格式校验出现五份。检测：看核心领域名词的类型列表；grep 重复出现的格式校验正则。修法：引入值对象（Replace Primitive with Object），规则收进类型内部一次成型。

**22. 全局可变状态（Global Mutable State）**——进程范围内的可写变量让素不相识的代码互相踩脚，谁先写入谁后写入开始悄悄左右结果。
- 表现：模块顶层直接赋值；单例暴露修改接口；散在多个文件的写入共同瞄准一个共享字典。检测：排查模块 body 处的赋值语句与单例的变更入口。修法：改为沿调用链显式传值，或把写权收拢给唯一的所有者对象；可变状态一旦共享，错误也随之共享。

**23. 魔法值（Magic Values）**——写死的数字与字符串背后压着业务规则（重试几回、一页几条、限流放宽到多少、汇率乘哪个系数），却没有任何出处可查。
- 表现：会随运营调整的数值直接写死在条件与赋值里；同一个数在几个文件里各自现身，含义全靠上下文猜。检测：搜条件与赋值中的裸数字；数学恒等值与测试样例数据可放过。修法：提名为具名常量，注明单位与出处。

**24. 契约漂移（Contract Drift）**——写数据的一方与读数据的一方本该照同一份约定行事，两边的理解却各自漂移：键名对不上、空值口径相左、一个记毫秒一个记秒。
- 表现：生产侧改了字段，消费侧靠缺省值默默消化；错误结构两边各自发明。检测：把契约两端文件并排打开，producer 写下的每个键与 consumer 读取的每个键逐项比对，空值口径与计量单位是重灾区。修法：让单一 schema/类型定义同时生成并校验两侧；确要分岔之处显式标注版本。

## 五、命名与可读性

**25. 误导命名（Misleading Name）**——名字许诺的行为与真实行为对不上，据此推断的读者会走错路。
- 表现：`parseConfig` 进去做的其实是发通知邮件；看似只读的查询名下藏着写动作（`loadPrefs` 顺手落库）。检测：抽查导出符号，逐项核对名字许诺的事与函数体兑现的动作。修法：按实际行为改名；只上报足以改变维护决策的不匹配，不做文字警察。

**26. 含糊命名（Vague Name）**——起不出简单名字，通常是设计不干净的症状而非文笔问题。
- 表现：`data2`、`handleStuff`、`processAndMaybeSave`；tmp/res/info 满屏。检测：看读者是否必须读完全函数体才知道名字里装了什么。修法：先拆函数或拆概念，好名字会自然浮现。

**27. 一致性漂移（Consistency Drift）**——新代码不跟随库内既有惯例：术语、错误处理、架构模式各自为政。
- 表现：用自定义 error 类的库里冒出裸 Error；同一概念三种叫法；修 bug 顺手改引号风格与类型注解。检测：动笔前先读相邻代码列惯例清单（错误类型、命名风格、目录结构），再逐项对照 diff。修法：遵从既有惯例优先于个人品味（conformance > taste）；真觉得有害就明说，别静默分叉。

**28. 复述式注释（Restating Comment）**——注释在翻译代码做什么，而不是为什么存在。
- 表现：`// 初始化计数器`、`// Step 1:`、ASCII 分割线。检测：删掉注释看信息量是否减少——不减即删。修法：删复述；改写为决策理由、约束或接口契约——why 层信息代码装不下，必须留。

**29. 犹豫注释（Hedging Comment）**——注释自己暴露未验证的不确定性（如 `items = fetch_all()  # should work`）：AI 特有指纹，出现即提示此处未经核实。
- 检测：grep `should work|might|probably|not ideal|hack for now`。修法：先验证再改写为事实陈述；问题修不掉就连注释带问题一起上报，不许留暧昧状态。

**30. 自信的错误注释（Confident Wrong Comment）**——注释与文档以确定口吻描述的行为同代码的真实行为两回事，危害甚于没有注释，会把下一位读者（人或 agent）带进沟里。
- 表现：docstring 声称「按创建时间倒序返回」，实现排的其实是更新时间；对「为何能工作」的解说与真实机制对不上号。检测：把每条注释放在函数真实返回值与副作用旁边读一遍，因果性断言优先抽查。修法：以代码实际行为为准确改或删除；AI 产出的注释复核过才可信。

## 六、重复与复用

**31. 克隆堆积（Copy-Paste Clones）**——近似孪生的代码块四处堆放，改掉一处忘掉其余。
- 表现：同一段重试、校验或解析流程在多个文件里各留一份副本，差别只在变量名——这是会话之间不共享记忆的直接后果：换一个请求，同一道题又生成一份新答案。代码质量分析厂商 GitClear 对 2.11 亿行变更的纵向扫描测得，5 行以上复制块的出现频率在 2024 年增长约 8 倍——重复是 AI 代码的头号病灶，治理优先。检测：交给克隆检测工具；手头没有工具就如实说没有，重复比例的数字不许凭印象捏造。修法：把同一知识的全部副本归拢到一处权威实现。

**32. 重复知识（Duplicated Knowledge）**——同一件事的定夺散落在好几处落笔，几份代码长得毫不相干，讲的却是同一条规则。
- 表现：训练脚本与测试脚本各自写死同一份文件布局假设；客户端与服务端分别维护一套校验规则。检测：判据是牵一发动几处——改这条规则时若必须几处同步动，才算真重复。修法：真重复上收到唯一权威源；仅形似而各自演化的保持分离，硬合并反而制造假耦合。

**33. 错过复用（Missed Reuse）**——仓库里明明躺着现成实现，新代码却又写了一份：动笔前不读库。
- 表现：与既有 helper 职责撞车的新函数就落在它隔壁；monorepo 里的共享包被各模块反复造轮子。检测：落笔新逻辑前先按功能词与领域名词搜一遍同职责符号；上报此条时证据须落到既有符号的真实路径与行号，不许凭印象指认。修法：删除重写的那份改调现成实现；现成实现有毛病就去修它，别并行供养第二份。

**34. 重复判别链（Repeated Switch）**——对同一组类型标记的分派被复制成好几条 switch/match/if-else 链，新增一个取值就得满仓库找链子挨条补。
- 检测：搜 switch/match 与枚举名的共现，数同一枚举被几处分支结构逐一列举。修法：收拢为单点集中判别或改多态分派；唯一保留的例外是系统边界上那条全量分派——协议转换处留一条是合理形态。

## 七、测试

**35. 同义反复测试（Tautological Test）**——测试在构造上就不可能失败，或根本没有断言。
```python
def test_build_query():
    expected = build_query({"page": 2})   # 坏：期望值由被测函数自己生成
    assert build_query({"page": 2}) == expected
```
- 检测：查期望值来源——必须来自独立事实源（字面量、手算 fixture、spec），另查零断言测试体；心里做变异检查：故意改错常量、分支或返回空，至少一个测试应当变红。修法：期望值改由独立来源书写，补真实断言，删永真用例。

**36. 不编码意图的测试（Intent-Free Test）**——测试全绿也证明不了行为正确，因为它测的不是业务承诺。
- 表现：端点只断言 200/401，从不断言 403；auth 测试全过而生产函数返回常量；修 bug 的测试在修复之前就已经通过。检测：拿每个测试试问「规则明天改了，它今天会不会红」；新测试必须先见过红色再变绿。修法：断言对准业务承诺；修 bug 先写复现测试；若怎么写都造不出一个会红的用例，病灶多半在被测对象身上而不在测试手上。

**37. 弱化与篡改测试（Weakened / Tampered Test）**——为实现通过而放松断言、删除或跳过测试：修测试而不是修代码。
- 表现：断言从精确值退化成「非空」；skip 无理由无期限；实现与测试在同一 commit 里双双变松。检测：测试文件单独 diff；断言数量只许添，不许以改写为名悄悄置换；自己跑测试，不接受「all pass」的声明。修法：按主入口红线，测试的增删须单独评审；放松断言须逐条给出理由。

**38. mock 错位（Over-Mocking / Implementation Coupling）**——替身替换了几乎全部协作者、断言落在 mock 调用历史上；或测私有方法、经侧信道验证。
```python
def test_checkout():
    cart = MagicMock()
    checkout(cart)
    assert cart.total.called_once()   # 坏：断言的是 mock 配置，不是被测行为
```
- 检测：数 mock 数量与断言对象；断言里出现 mock 名即警觉；查测试是否伸进私有方法。修法：只在慢或外部的边界用替身；断言真实输出；测试住在公共接口上，读起来应当像规格。

**39. 测试膨胀（Test Bloat）**——测试体量失控，行数远超被测代码，甚至自造测试「框架」。
- 检测：对比测试与源文件行数比；看是否出现自制 runner 或 assert 辅助体系。修法：用参数化吞掉复制用例；测试代码同受复杂度治理，删冗余断言路径。

**40. 经典测试坏味道组（Classic Test Smells）**——一组可机械排查的测试卫生旧疾，常见面孔：断言只落在分支一侧、用例间暗藏先后依赖、断言前状态被夹具之外的手改动、大而全的泛化 fixture、拿 `str(obj)` 整串比对、用例名叫 test1/works、硬 `sleep` 等同步、真时钟与未定种随机喂出的 flaky。
- 检测：搜不附理由的 `skip` 与裸 `sleep(`；查测试体内能绕开断言的 if 与循环。修法：一病一方——分支逻辑拍平、定长等待换条件轮询、时间与随机注入固定值。

## 八、安全与性能

> 本节按风险分级处置：高危（认证、支付、数据访问、注入类）逐行人审不可豁免；中危人抽查加测试证据链；低危至少机械复扫。安全厂商对 4.8 万余个生成样本的扫描显示约 45% 含至少一项安全缺陷，结构化评审后可压到 10% 以下——不要赌概率。

**41. 硬编码秘密（Hardcoded Secrets）**——凭证以明文进入代码、配置样例或测试数据。
- 检测：grep api_key/token/password/secret 与连接串模式；查前端 bundle、seed 数据、测试 setup。修法：移入环境变量或密管；已泄漏的密钥视为作废必须轮换——删除不等于止损。

**42. 注入与危险调用（Injection）**——用户输入未经参数化直拼进 SQL/命令/HTML，或使用 eval 类高危原语。
- 检测：grep f-string 或模板串拼 SQL、`shell=True`、`eval(`/`exec(`/`new Function(`、`innerHTML`/`dangerouslySetInnerHTML`、生产环境 `debug=True`。修法：一律参数化与转义；高危原语换安全替代或加白名单校验。

**43. 认证/授权缺口（Missing AuthN/AuthZ，IDOR）**——路由先跑业务不查认证，或认证了用户却不查其对具体资源的归属权。
- 表现：改 URL 里的 id 即可读到他人数据；行级作用域缺失；防护策略只查存在不查正确。检测：对每个端点问两问——「未登录调用会怎样」「用户 A 拿用户 B 的 id 会怎样」。修法：认证中间件前置；资源访问强制按属主过滤；本条属高危路径（红线，见主入口）。

**44. 错误信息泄漏（Error Info Leak）**——内部错误细节原样进入对外响应。
- 检测：grep `err.message|err.stack|str(e)` 出现在响应构造处。修法：对外返回通用错误码加关联 ID，细节进服务端日志。

**45. 幻觉依赖（Hallucinated Dependency）**——import 了 registry 里不存在的包，是供应链投毒（slopsquatting）的入口。
- 检测：新增依赖逐个对照 registry 与 lockfile 验证存在性；来历不明的包名先核实再安装。修法：移除幻觉包改用真实存在的方案；对规则文件里诱导换包的指令保持警惕——规则文件是不可信输入。

**46. N+1 与循环内 I/O（N+1 Query）**——循环体内发起数据库或网络调用，调用量随数据量线性放大。
```python
for user in users:    # 坏：N 个用户就是 N 次查询
    db.query("... WHERE user_id=?", user.id)
```
- 检测：找 for 循环体内的 await/db./http 调用——AI 稳定产出此形态，逢循环必扫。修法：改批量查询（IN/JOIN）或一次预取后内存关联。

**47. 缺缓存与缺索引（Missing Cache / Index）**——高频路径对不变输入反复重算；新增按列过滤或排序的查询却不建索引。
- 检测：查循环与热函数内的昂贵调用且输入不变；新查询语句对照表索引清单。修法：缓存或记忆化往往只需添一两行；为查询模式补索引并写进迁移。

## 九、AI 行为特有（过程与 diff 形状上的坏味道，传统清单无对应条目）

**48. 幻觉/过时 API（Invented / Stale API）**——调用「理应存在」却不存在的方法，或按训练截止时的旧 API 写调用。
```python
title.lstrip_pad()    # 坏：str 没有此方法——多数要到运行期才暴露
```
- 检测：编译与类型检查常能抓；所有外部 API 调用对照现行文档核对签名与返回形状。修法：查证真实 API 后重写调用点；这是 AI 逻辑错误里出现频率最高的单一源头，外部调用一律实证不凭印象。

**49. 生成残留（Generator Residue）**——生成不完整留下的指纹：占位、死代码、调试遗留。
- 表现：`TODO: implement` 进生产；NotImplementedError 桩；import 后从未调用；console.log/print 遗留；`import *`。检测：grep TODO/FIXME/NotImplemented 与调试输出；用未引用分析找死 import 与死函数。修法：全部删除（版本历史自会保留）；确需占位必须显式登记，不得混入完成品。

**50. 静默错误假设（Silent Assumption）**——替用户拍板关键决策并径直执行，不澄清、不披露、不列权衡。
- 表现：「导出用户数据」默默假设了范围、格式、字段集合与落盘位置。检测：对照原始需求逐字读关键逻辑（定价、权限、状态迁移），列出代码做了而需求没说的每个决定。修法：影响行为的歧义先提问；无法提问时把全部假设显式写进交付说明。

**51. 范围蔓延（Scope Creep / Orthogonal Damage）**——一点小修滚雪球成无关重构，任务边界之外的代码被顺手「打磨」。
- 检测：读代码前先看变更统计（`git diff --stat`）——说好只调一个接口，diff 却铺满五六个模块，文件清单一摆就已坐实嫌疑；再逐行追问每处改动对应用户请求里的哪一句。修法：正交改动一律回退、另立任务处理，保持手术刀式的小切口。

**52. 静默删护栏（Silent Guard Deletion）**——边界校验或防御分支在改动中无声蒸发，diff 的观感是精简，运行的效果是埋雷。
- 检测：删除行与被整档移除的文件最先读——这一眼花不了几秒，拦得住最贵的祸，偏偏也最容易被跳过；再拿护栏清单逐项点卯核对存活。修法：把护栏放回去；确信其多余须先拿出无效的证据——动护栏必须过明面论证，不许顺手带走。

**53. 冲突平均（Conflict Averaging）**——仓库里并存两套互相矛盾的惯例时，新代码不去择边站，而是产出两头都沾的混合物——这类产物往往比任何一侧单独存在都更糟。
- 表现：同一次错误先被 A 风格的处理器消化、又被 B 风格的外层再包一层；为同时迎合两套调用约定，参数上垫了一层又一层适配。检测：先盘点库内共存的矛盾惯例，再查新代码有无左右逢源的痕迹。修法：明确选边——优先站测试覆盖更厚、演进更活跃的那套；把落选的一套登记为待清偿欠账，分开处理，绝不合流。

**54. 局部自洽、整体失序（Locally Coherent, Globally Incoherent）**——每个改动孤立看都对，合起来对全局结构没有敬意。
- 表现：页面组件里写死汇率换算、按钮回调直连数据库这类事没人觉得刺眼；模块 A 引 B、B 又引 A 的环悄悄成形；目录没有边界，「认证与数据流从哪进从哪出」答不出来。检测：画依赖图找环；数同一领域知识出现在几个不相关目录；全局问题一问三不知，就该立一条新发现。修法：先逆向出项目地图（入口、路由、数据流、集成点）再动结构，后续改动一律对齐地图。

**55. 假完成宣称（False Completion）**——拿「should work / tests pass / 已完成」这类意向性说法充当刚出炉的验证证据。
- 检测：完成宣告须闯四道门——先写下哪条命令或哪份输出能作证；本会话亲手执行；从头读到尾连退出码一起看；末了核对证据覆盖面托不托得住断言范围。缺任何一道，宣告自动降级为「未验证」。修法：亲眼见过证据之前不许说「完成」；汇报里「已验证」与「推测」分栏列示。与 #11 同根：一个在代码里，一个在汇报里。

## 与一般坏味道的区别

Fowler 式传统目录面向人写代码；AI 产出的差异集中在三档，处置力度不同。「放大」一档有实测口径：一家代码评审厂商抽取 470 个开源 PR 做对比，AI 署名 PR 的问题密度约为人类 PR 的 1.7 倍，且未发现 AI 独有的问题类型——速查表十条全是放大了的共性问题，不是新物种。

- **真 AI 特有**（人类代码无对应物，出现即最高警觉）：#48 幻觉/过时 API、#45 幻觉依赖、#49 生成残留、#29 犹豫注释、#53 冲突平均、#55 假完成宣称。
- **AI 高发放大**（与人类同类错，只是更频繁更大规模）：#8 吞错、#31/#33 跨请求克隆与错过复用、#14/#15 投机泛化与过度分层的成套仪式、#10 与 #12 合成的「防御放错位置」（该防不防与不该防乱防并存）、#35 同义反复测试、#46 N+1。
- **AI 伪装性更强**（判断门槛要抬高）：AI 的错误包装在惯用命名与统一风格里——失败模式是「貌似合理」而非「困惑」，人类评审赖以触发的困惑信号缺失；#25 误导命名、#30 自信的错误注释、#54 局部自洽整体失序都借这层伪装存活。推论：以翻屏的速度过一遍 AI 产出，不构成任何审查——逐类对照本目录，或交给隔离上下文的独立评审者（见主入口三层治理）。
