# 评审参考：AI 代码评审与人审协同

> 何时读我：变更完成、需要独立评审把关时（无论作者是 AI 还是人）；要派子代理做独立评审、需要知道给它什么输入、怎么约束它时；需要决定一处变更该人审到什么深度（逐行 / 抽样 / 半黑盒）时；怀疑测试是「假测试」、要验证保护网成色时；拿不准该不该信 AI 对自己代码的解释时。

## 一、评审者纪律（先于看任何代码）

1. **绝不在生成者的会话里评审它自己刚产出的代码。** 生成者给自己盖章，是用同一套偏差确认同一套偏差。评审者必须开新会话或独立子代理，与生成过程零共享上下文——这条「生成与评审分离」铁律不可协商。
2. **评审者的输入 = 变更 diff + 方案中的意图与约束（或等价的意图说明），绝不含生成者的会话历史。** 历史里全是生成者的自我辩护，喂进去等于预装偏见；diff 与意图说明是刻意配好的剂量——太少缺语境，太多带立场。
3. **对每条检查规则输出四值判定：符合 / 违反 / 未涉及 / 证据不足。** 禁止把「看不出来」硬挤成「违反」；「证据不足」是合法结论，留它一席之地，是为了让评审者可以空手而归，不必为凑数硬造发现。
4. **防过度报告是生存纪律。** 评审报告的信用是一次性资产：读者被假警报骗过两次，就永久不再读你的任何报告。每条发现报出前自问三遍：机器能查到吗？真的影响行为吗？我给得出证据吗？任何一问答「否」，删掉。
5. **每条发现标注证据分级：机械（工具输出可复现）/ 语义（评审者判断）/ 估算（工具缺失时的降级推断）。** 估算永远不许标成机械；工具没跑就写「未测」，绝不编数字。
6. **发现自己开始走马观花就停下。** 浏览过一遍不等于审过一遍：草草扫视过的代码与从未看过的代码，风险没有差别；感觉省下的时间，只是把代价推迟到线上。换更小的 diff 再来。
7. **审 AI 代码的强度不得低于人写代码。** AI 的错误没有困惑信号——错得再离谱，语气也一样自信；表面合理的代码比明显烂的代码更耗心神。
8. **测试与验证产物的增删必须单独 diff 并说明理由，作者会话不得顺手改动它们。** 防的是「改测试迁就代码」这类自我通关。

## 二、反误报清单（报出前逐条自查）

先立正向筛子：一条问题须同时满足两个条件才值得报——机器查不出，且影响正确性、安全或可维护性；省下的注意力全部投向机器查不出的部分。

再过反向清单，以下类型一律不报或降级处理：

- linter、类型检查器、编译器、CI 会抓的：缺失或错误的 import、类型不匹配、格式问题。不要重复机器的工作。
- 本次 diff 之前就存在的存量问题。评审的职责是这次变更，不是全库清查。
- 学究式挑刺：资深工程师会皱眉「这也报？」的，删掉。
- 纯风格偏好：想提就标 Nit，并接受被无视。

严重级三档：**Must**（阻断合并）/ **Optional**（建议修复）/ **Nit**（微瑕，作者可无视）。分级要诚实——把 Optional 全标成 Must 是另一种形式的过度报告。与审阅深度三档大致对应：高危↔Must、中危↔Optional、低危↔Nit，按实际影响定档。

## 三、评审母表（八维度清单）

维度顺序即优先级：意图与范围、安全、逻辑与错误路径每次必查；其余按触碰面加查。分工原则：能逐条枚举的核查全部让机器做，评审者把时间花在机器答不上的问题——这个改动是不是在解决对的问题、与这个系统合不合拍；此类判断题没有自动化替身。高危项以【高】标注。

**意图与范围**
- [ ] 范围先行：需求只提到两三个文件、`git diff --stat` 却铺开十几处，光这个形状出入就够立一案——先把「为什么动这些」问清楚，再往下读代码
- [ ] 先读删除行：被删的护栏、边界分支、校验最容易被忽略——行数往下走的观感，盖不住安全网被剪开的事实
- [ ] 让每行改动可追溯到需求；顺手「改进」无关代码、注释、格式是正交伤害，要求回退
- [ ] 对定价、权限、状态迁移等关键逻辑，把代码对照原始需求逐字读，查「实现的是字面还是意图」
- [ ] 需求文档没写到的行为，按一个真实用户会怎么使用它来评判——文档没写不等于允许

**安全**
- [ ]【高】用户输入拼接 SQL、shell 命令、文件路径处，查参数化与白名单
- [ ]【高】用户输入渲染进 DOM 或模板处，查转义；dangerouslySetInnerHTML 与裸模板串同罪
- [ ]【高】每个新端点确认先认证再进业务；认证 ≠ 授权——换个 URL 里的 id，能不能摸到别人的数据
- [ ]【高】在 diff 里搜硬编码凭据（密钥、token、连接串），示例代码与数据初始化脚本一并翻——示例账号混进真实凭据的事故，多半从那里开始
- [ ]【高】新增依赖核对三件事：真实存在（幻觉包是投毒入口）、仍在维护、许可证兼容
- [ ] 查架构级暴露：凭据不进前端产物、客户端不直连数据库、安全策略验证的是「正确」而非「存在」

**逻辑与错误路径**
- [ ] 沿数据流逐步查 null 与类型；类型断言只是让检查器闭嘴，不算处理
- [ ]【高】逐个追查 catch：接住异常却既不落日志也不往外抛，就是无声失败；资金与计费链路上吞错，等于让钱无声漏走
- [ ]【高】外部 API 调用逐个对照现行官方文档核签名与行为——模型记忆里的接口停在训练截止那天，凭印象写集成是其逻辑错误的高发源头
- [ ]【高】给并发出题：同一份资源同时被两个请求改写，会落得什么结局；「应该撞不上」不算冲突处理
- [ ] 下游失败时，异常是原样上抛、翻译成调用方认得的错误类型、还是落日志后继续走，必须与双方约定一致，不许临场发挥
- [ ] 像用户一样过边界值与极端路径；UI 变更光读代码判不了影响，要求演示或验证

**测试有效性（专项展开见第五节）**
- [ ]【高】测试文件单独 diff：断言数量是变多还是变松、被删、被 skip——放松的断言最爱藏在合法实现改动旁边
- [ ]【高】自己跑测试，不接受「all tests pass」的声明；那份声明本身就是被审对象的产物，不能给自己作证
- [ ] 期望值必须来自独立事实源（手算 fixture、字面量、需求文档），不是被测代码自己算出来的

**复杂度与设计**
- [ ] 先问「能否删掉」：超出当前需求的通用化、为假想未来准备的扩展点，一律推定有罪、要求显式辩护
- [ ] 区分「同一知识」与「偶然相似」：两处编码同一条业务规则才是真重复，必须收敛为单一权威表示；碰巧长得像的强行合并是制造错误耦合
- [ ] 查错过复用：先 grep 库里既有的 helper，找到了就要求替换新造的那份
- [ ] 查决策散射：同一个设计决定散布多模块（改一处要追五处）是结构性坏味道
- [ ] 拉远看系统：这个变更让代码库更可维护，还是又叠一层要还的债

**命名与注释**
- [ ] 名字对照实际行为：叫 checkBalance 的函数若实际做的是冻结账户，后来者会顺着名字一路误会下去
- [ ] 注释对照实际行为：AI 会自信地写错注释——「返回全名」挂在返回 ID 的函数上，比没有注释更糟
- [ ] 让注释承载 why（决策理由、陷阱、单位与边界），删掉复述 what 的注释
- [ ] 一遍短读说不清「这段做什么」「这个测试挂了意味着什么坏了」，就是发现——清晰与否由陌生读者裁定，不由作者自评

**一致性与卫生**
- [ ] 把新代码放进周围代码的语境读：周边模块对外都抛带错误码的异常类型，新代码却抛裸 Error，就是破坏约定；宁跟惯例，不炫新写法
- [ ] 对齐领域术语：同一个概念不允许出现第三个名字，与项目词汇表核对
- [ ] 删净死代码（版本控制记得一切）：无用 import、注释掉的代码块、生成残留
- [ ] 把携带领域含义的裸字面量（超时、限额、状态值）提为具名常量
- [ ] 改了接口行为、构建方式、发布流程，要求同步文档；删代码时查文档是否该删

**性能与资源**
- [ ] 高频路径上的重复昂贵计算：同样输入每次都重算一遍，先确认能否记住结果——这类修复往往只动几行，收益却最稳
- [ ] 查询方式变了，索引要跟上：按哪个字段筛、按哪个字段排，就查有没有对应索引；这一步最容易被「功能已经对了」掩盖
- [ ] 数循环体里的查库与外呼次数：每转一圈打一次数据库的写法，小数据跑得通、大数据必然倒——先批量取数再处理是默认正解
- [ ] 挑战新依赖的必要性：标准库几行能做的事，不引入一个包

## 四、风险 × 可验证性分级

| 分级 | 适用路径 | 审法 |
|---|---|---|
| 高危 | 认证、支付、数据访问、安全、并发 | 人审且逐行，无可妥协；不因「有测试」豁免 |
| 中危 | 业务逻辑、对外行为变更 | 独立 AI 评审 + 人抽样 + 测试证据链 |
| 低危 | 内部工具、原型、一次性脚本 | 半黑盒信任：用运行结果说话，事后抽查 |

- 可验证性高（关键路径测试覆盖充分、行为有金丝雀监视）可降一档；测试薄弱则升一档。
- 警惕「偏差正常化」：低危路径每次放过的小问题，都在抬高你下一次的默认底线——今天放过 200 行的函数，明天 300 行的也显得正常。事后抽查必须真的发生，并追问「这次放过的，上次是不是也放过了」。

## 五、测试有效性专项

- **假测试特征**，命中任一即要求重写：
  - 没有断言，或断言停在「不抛错、有返回」这种装饰级别；
  - 期望值由被测代码自己算出——同义反复，怎么跑都过；
  - mock 了一切，测的是 mock 的行为，不是被测代码；
  - 删掉断言换成 print，靠人眼看输出过关；
  - 无理由、无期限的 skip；用 sleep 硬等凑时序。
- **没见过它失败的测试，不算保护网。** 全绿的套件只证明它会通过，不证明它能抓错。成色只有一个判据：相应的代码坏了，它会不会红。
- **金丝雀自检**：故意破坏一行（改错一个常量、反转一个条件、删一个关键副作用），跑测试——必须有测试变红，然后复原。破坏没人察觉，说明保护网是空的，先补网再继续。
- mock 原则：只在慢或外部的边界替换；mock 必须完整镜像真实数据结构——部分 mock 会在下游读缺失字段时静默通过。

## 六、跨模型评审

- 跨模型评审有效但**方向敏感**：有实验（116 道编程难题，评审者只看题面与草稿）支持「Claude 审 Codex 草稿」方向（约提升 18 个百分点），同一实验里反方向「Codex 审 Claude」不升反降。
- 换用任何新的模型组合前，先拿小样本验证方向有效再铺开；不要默认「多模型互审总是好」。
- 无论结论来自哪个模型，**人工抽查是终审**：AI 评审的价值是过滤与排序，不是裁决。

## 七、对 AI 解释的审查

- 解释和代码是同一支笔写下的：解释写得自信，不代表代码写得对。把解释当「待核实的线索清单」，不当「质量证明」。
- 每次评审抽查至少一条**可验证的事实主张**：声称的依赖包在官方 registry 里存在吗？声称的 API 签名与现行文档一致吗？声称调用的内部函数真的存在吗？
- 抽查命中一条假主张，就把其余解释与代码全部按「不可信」处理、逐段重读。示例：AI 解释「这里调了框架的 retryAll 钩子」，一查文档根本没有这个钩子——那行代码从未按解释的方式工作过。
- 评审文化：引用任何质量数据前先过一遍方法学——谁测的、样本是什么、口径含不含功能错误；来源说不清的数字，只当轶事听。

## 八、评审意见格式（最小示例）

每条发现按以下字段组织，四字段加严重级，缺一不可：

```
- 位置：src/pay/charge.ts:42（commit a1b2c3d）
- 问题：支付失败被 catch 静默吞掉，对上游返回成功
- 证据：语义——该分支无日志、无重抛；对照需求「失败必须通知用户」
- 严重级：Must【高】
- 建议：失败时进重试队列并通知用户；补「支付失败 → 用户收到通知」的测试，并先看它失败
```

收尾附四值判定汇总：母表各维度规则 → 符合 / 违反 / 未涉及 / 证据不足（后者注明还缺什么证据）。
