# vibe-quality：AI 生成代码的质量治理

> 何时读我：任何涉及代码质量的工作开始之前——体检、评审、重构、清理、新任务开工、配护栏。本文件只做两件事：立不可妥协的红线，把具体的活路由到子文件；细节一律不在这里展开。

## 立场：AI 代码默认「能跑，但不可维护倾向高」

AI 生成的代码能编译、能跑通主流程，却稳定带病：膨胀、重复、过度分层、防御放错位置、测试薄弱。
更麻烦的是错误包在自信流畅的风格里，没有人类代码那种困惑信号——流畅的外表会冒充内容的可靠，快速过一遍常常只是快速错过。
对一家代码评审厂商 470 个 PR 的对比实测，AI 变更的问题密度约为人类的 1.7 倍；把它当工作假设，别当豁免理由。
本 Skill 不赌模型自觉，把质量治理拆成可执行的流程：审计、评审、重构、工作流、护栏各管一段，每一步要证据、可追溯。
目标不是超越人类，而是靠流程稳定达到并保持「人类工程师可维护」水准——可解释、可测试、可演进。

## 三层治理总原则

约束的强度天然分层，冲突时上层压下层，治理投入优先给上层：

- **流程门（最强）**：验证证据、测试门、独立评审、档位分级——约束长在流程的必经之路上，想宣称完成就得过门。
  它防的是结构性风险，不随模型变强而放宽：模型越强，越容易把错误藏进看起来更漂亮的实现里。
- **独立评审（次强）**：命名、抽象、何时提问这类判断题无法脚本化，兜底是隔离上下文的评审者加四值判定。
  为什么必须独立：同一个会话自查，查不出同一个会话的盲区——偏差会自我确认。
- **规则文本（最弱）**：常驻提示只是请求，会被长会话稀释、被压缩遗忘；两条规则冲突时模型会双双忽略。
  所以少而硬，关键条款必须有上层接住，不能只住在文本里。

## 红线（全 Skill 仅此处集中列出一次）

凌驾于一切流程之上，触发即停下、交人裁决。子文件按各自语境提到同主题时措辞不同、意思一致，冲突时以更严者为准。

1. **行为保持**：重构只改「怎么做」，不改「做什么」——返回值、副作用、错误形态一件不许变。
2. **评审独立上下文**：绝不在生成者的会话里评审它自己的产出；评审者的输入 = 变更 diff + 方案中的意图与约束（或等价的意图说明），绝不含生成者的会话历史。
3. **测试不可单方篡改**：测试与验证产物的增删改须单独 diff 并说明理由；作者会话不得顺手放松断言、删测试、加跳过。
4. **高危路径人审**：认证、支付、数据访问、安全、并发——人审且逐行，不因「有测试」豁免。
5. **无证据不下结论**：每条结论回溯到执行过的命令或具体行号；没有本会话新鲜执行的验证，不得宣称完成。
6. **删除行必先读**：先逐行读被删代码与被整删的文件——瘦身式 diff 未必是精简，可能剪断的是保险丝。
7. **新依赖先核实**：对照官方 registry 验证存在性与维护者；幻觉包是供应链投毒的入口。
8. **范围外不动**：每行改动可追溯到用户请求；方案清单外的文件一个不碰，正交的「顺手改进」一律回退。
9. **原型重写须显式声明**：允许整段重生成的只有显式声明「这是原型」的代码；拿不准一律按长期维护处理。
10. **规则文件人维护**：AI 只提议 diff，合入必须过人眼；让 AI 直接治理规则文件，条目必然只增不减。

## 路由表：什么时刻读什么

| 场景 / 时机 | 读什么 |
|---|---|
| 拿到一块既有代码（多为 AI 生成或深度参与），要产出带证据的问题清单 | `references/audit.md` |
| 审计、评审或清理中逐类对照坏味道；动手修之前查对应条目的「修法」 | `references/smells.md` |
| 被要求重构、清理、简化、精炼，或抱怨代码膨胀、重复、过度分层、看不懂 | `references/simplify.md` |
| 接到任何编码任务、动手之前——分级、澄清、方案、执行、收尾全程怎么走 | `references/workflow.md` |

| 要把某条「必须」变成真约束：hooks、pre-commit、CI、规则文件、上下文治理 | `references/guardrails.md` |

脚本是证据收集器，不是裁判：它圈出「值得看一眼」的可疑点，是否构成坏味道交给语义层与坏味道目录判。

读本 Skill 的纪律：只读被路由到的子文件，不预加载全部；子文件之间只在必要处用一句指针互引（如审计对照坏味道目录），不整篇预加载；跨域一律回到本表；审计、评审、重构是三种角色，一批工作只担任一种。

## 三个典型工作流

**场景一：AI 写完一坨代码，要体检或治理。**

1. 判存活特征（真实用户、外部集成、测试三查）定口径：长期维护还是原型——见 `references/audit.md`。
2. 划文件清单请人确认；要扫全库先给理由与成本预警，没有边界的审计必然失焦。
3. 跑 `scripts/quality_scan.py` 收机械证据，按风险抽样深读，对照 `references/smells.md` 逐类判定。
4. 产出报告：每条四值判定加四栏发现格式（位置、问题、证据、建议），高危置顶，覆盖度如实声明；审计不改一行代码。
5. 修复决策交人；获批后切 `references/simplify.md`：先补特征测试，再小步走。
6. 逐行读删除行，安全发现优先于一切结构改进；高危路径批次交人逐行复审后才算完。

**场景二：接到新开发任务，按质量流程做。**

1. 第一件事是分级不是写码：影响面、风险路径、核心程度三判据定 T1/T2/T3——见 `references/workflow.md`。
2. 过澄清门：先重述需求请人确认；提问最多 3 个且带倾向答案；每个默认选择写进假设清单。
3. T2/T3 出五件套方案，验收标准必须是「跑哪条命令、断言什么输出」的可执行检查。
4. 执行小步走：每步开工前一句话讲清目的，收口交给秒级裁判（类型检查、lint、相关测试），红了退回拆小重试；台账外置，恢复工作靠台账不靠回忆。
5. 盯四个停机条件，触发任何一条立即带清单回来，绝不悄悄绕过。
6. 收尾：清生成残留、跑全量测试留新鲜证据、按「改了什么 / 如何验证 / 剩余风险 / TODO」四件套汇报。

**场景三：要评审一段 AI 生成的代码。**

1. 开新会话或独立子代理：评审者的输入 = 变更 diff + 方案中的意图与约束（或等价的意图说明），绝不含生成者的会话历史——细则见 `references/review.md`。
2. 先看 `git diff --stat` 查范围蔓延，再读删除行查静默删护栏，然后过反误报清单。
3. 按八维度母表逐项查：意图与范围、安全、逻辑与错误路径每次必查，其余按触碰面加查。
4. 测试文件单独 diff；自己跑测试，不接受「all pass」的声明。
5. 抽查至少一条可验证的事实主张（依赖存在吗、API 签名与现行文档一致吗）；命中假主张，整段按不可信重读。
6. 每条 finding 按四字段组织并标严重级，收尾附四值判定汇总；高危路径升级为人审逐行。

## 术语速查

- **坏味道**：可命名的结构病灶（吞错、克隆堆积、投机泛化……）——有名才能被系统地查与修。
- **护栏**：住在模型上下文之外的强制（沙箱、hooks、CI）；提示是请求，钩子是保证。
- **行为保持**：对外部世界可见的一切不变——返回值、副作用、错误形态、时序。
- **特征测试**：把当前观察到的输入-输出对照固化成断言，是重构前的保护网。
- **证据分级**：机械（工具可复现）/ 语义（判断落到行号）/ 估算（诚实降级），低级永不冒充高级。
- **四值判定**：符合 / 违反 / 未涉及 / 证据不足——第四值专为防过度报告而生。
- **风险分级**：高危逐行人审、中危 AI 审加人抽样、低危半黑盒——漏一个高危远贵于多审十处低危。
- **独立评审**：与生成过程零共享上下文的评审；同会话自查等于让作者批改自己的作业。
- **上下文外置**：关键状态（台账、约束、记忆）落进文件与配置，不赌会话记忆能活过压缩。

## 诚实边界

本 Skill 是提示层约束，不是保证——它依赖模型愿意遵循，在超长会话中仍可能失守。
任何关乎正确性的「必须」，请配置成 hooks / pre-commit / CI 等确定性强制，配方见 `references/guardrails.md`。
可靠性来自多层冗余加关键节点人审，不来自一份写得足够好的文档。
