## 一、痛点（真实用户反复抱怨的）

1. **「局部正确、整体失控」**：AI 改动孤立看没问题，但对项目结构/邻近模式缺乏尊重。两年 vibe coding 复盘帖原话："Agents write units of changes that look good in isolation... respect for the whole, there is not."（hn-vibecoding-two-years-handwriting.md，865 分 634 评）
2. **Rules/CLAUDE.md 不被执行**："CLAUDE.md feels like more of a gentle recommendation... daily repeated failures, much apologies from Claude." 该 issue 7 个月无官方回应，新报告被机器人标记为重复后关掉（gh-claudemd-rules-ignored.md，45 reactions，链接 #2544）。压缩(compaction)后被忽略是常见诱因（#19471）。
3. **上下文丢失不可审计**：compaction 后既丢规则又丢历史，UI 无任何途径回看压缩前的对话，"Users cannot audit Claude's reasoning after compaction"（gh-compaction-no-review.md，89 reactions，#27242）。
4. **Review 通道本身会坏**：Cursor 2.5.17 起 agent 的多处修改不显示 diff、部分改动"auto-accepts without user confirmation"，用户："this is most critical feature, how did you come up to lose it"（cursor-forum-hidden-diffs.md，236 楼）。
5. **能力错位加速技术债**：初级用户让 AI 写超出自己理解水平的代码 → 单文件膨胀 → 出错后 100% 依赖 AI → AI 修不动时进入死胡同（reddit-chatgptcoding-top-year.md「The downside of coding with AI beyond your knowledge level」）。
6. **模型悄悄退化/降智**："Claude Code is unusable for complex engineering tasks"（#42796，3286 reactions，583 评）；Anthropic 员工回应猜测：1M 上下文开放后用户不再 /compact，>200k 后模型表现变差（gh-unusable-complex-tasks.md 内 @bcherny +714 下的讨论）。
7. **中文侧同样痛点**：掘金创业复盘作者——上下文一长 AI 忘记设计决策、改 A 坏 B、风格不一致、对质量"能跑就行"（juejin-ai-coding-startup-halfyear.md，仅抓到开头，线索）。

## 二、共识对策（多来源独立收敛的做法）

1. **先审计划、再放行代码**：Harper Reed 工作流核心是 spec→让 AI 向你提问("ask me up to 5 questions")→分阶段执行；评论称"was the magic ticket for me"（hn-harper-reed-llm-codegen-workflow.md，522 分）。
2. **测试/CI 作为 AI 的硬反馈环**："setup automated integration/e2e tests and feed that back into your AI agents before a human looks at it"（hn-ask-llm-coding-established-codebase.md）；Pythagora(GPT Pilot) 经验：verbose log 帮 AI 自查（reddit 合集帖）。
3. **用 AI 审 AI（跨模型/独立角色）**："I never trust the opinion of a single LLM anymore... always get a 2nd or 3rd opinion"（hn-vibecoding-two-years-handwriting.md @rtp4me）；GPT Pilot："agents can review themselves... works amazingly well"（reddit 合集帖）。
4. **让 AI 复述任务/验收标准再开工**："Does this make sense?" 迫使其重述问题，既校验理解又强化约束（hn-ask-getting-better-at-ai-coding.md @helterskelter）。
5. **规则文件从真实对话中沉淀**：先和 AI 结对改一处代码，再让它"based on the current chat"生成含理由的 rules 文件（同上帖 @serial_dev）；rules 的经验被反复验证有效但非 100%。
6. **人盯关键路径**：多位资深者共识——只让 AI 写"自己能看懂但懒得写"的代码；小步提交可回滚；worktree 隔离实验（hn-ask-llm-coding-established-codebase.md @weeksie: Claude Code + worktrees 是团队标准配置）。

## 三、争论点（正反方一句话）

1. **Vibe coding 值不值得作为工程方法**
   - 反方（Bram Cohen，BitTorrent 作者）："The cult of vibe coding is dogfooding run amok"——不在场内迭代就无法回答后续问题（hn-cult-of-vibe-coding.md，616 分）。
   - 正方：AI 只是又一层抽象，汇编时代的人也骂高级语言（同帖 @infinitewars）；反驳："High level languages are not black boxes"（@pavel_lishin）。
2. **文档/规范先行 vs 执行者自由裁量**
   - 争于 superpowers #895：计划过度指定实现细节，"leaving no room for executor judgment"，弱模型执行反而更蠢。
   - 维护者回应（obra 本人）：设计初衷就是让 haiku 级模型也能执行；试过放宽抽象层，评测结果"all worse"；怀疑正解是"interface contracts + nuance/intent + 关键处伪代码"（gh-superpowers-plans-overspecify.md，38 reactions）。
3. **一个 agent 跟到底 vs 多 agent/多模型分工**
   - 多模型派：单模型自评不可信，Codex/Gemini 交叉评审能揪出 Claude 的"significant critical oversights"。
   - 单线派：上下文 piping 成本吞噬收益，"I was spending all my time on context piping"（hn-ask-experimenting-llms-coding.md @zmgsabst）；superpowers 用户抱怨技能链拖慢响应（gh-superpowers-slowness.md #743）。
4. **AI 代码该不该重构、由谁 review**
   - 「我审美我做主」派： senior 天生看谁代码都不顺眼，LLM 写的照改不误（hn-vibe-vs-agentic-engineering.md @singpolyma3，787 分）。
   - 「能力边界」派：看不懂的代码没资格合并；也有评论者担心"AI eternal summer"——按 spec 达到 80% 后，收尾差距成为无止境的小修（@dv_dt）。
5. **IDE 该以人为中心还是以 agent 为中心**（Cursor 2.0，295 赞反对帖）："2.0 is steering me away from my code... I lose my sense of ownership"；官方：IDE 视图仍在，agent 视图只是默认项（cursor-forum-2.0-wrong-direction.md）。

## 四、反直觉经验

- 让 AI **先向你提问**比精心构造长 prompt 更有效（Harper Reed 帖多人复证）。
- 语音转文字输入 500 词长需求，比打字更完整地表达意图（@bogtog，hn-ask-getting-better）。
- **上下文越大未必越好**：1M 窗口诱惑用户不压缩，>200k 后性能下滑是"降智"体感来源之一（#42796 内部讨论）。
- LLM 生成的注释比代码更让人反感（"I don't understand how anybody stands comments generated by an LLM"，hn-vibe-vs-agentic-engineering.md @gabriela_c）。
- rules 不生效时 AI 的道歉反而成为新的噪音："daily repeated failures, much apologies from Claude"（gh-claudemd-rules-ignored.md）。
- 「写得快」争议：原帖作者称手写反而更快，高赞反驳称在新代码库/新语言下不可能（@sailfast）。

## 五、对中文 Skill 构建的直接启示

1. Skill 的规则要"可执行、可校验"，不能重蹈 CLAUDE.md「温柔建议」覆辙——配套测试/钩子强制比嘱咐式规则可靠。
2. 内置「AI 反问需求 + 复述验收标准」步骤（社区验证的 magic ticket）。
3. 提供「跨模型二评」或「独立 reviewer 角色」入口，但允许用户关闭以省 context。
4. 长会话提醒压缩风险 + 关键约束在压缩后自动重申（痛点 #2/#3 的直接解药）。
5. 计划文档粒度：接口契约 + 意图说明 + 关键伪代码，别把实现细节写死（superpowers 教训）。
