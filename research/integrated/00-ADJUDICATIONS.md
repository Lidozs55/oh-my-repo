# 主 agent 最终裁决记录（阶段 3 收口）

日期：2026-10-11。本文件对 A–E 五个整合域上报的全部待裁决矛盾作出最终裁决，是阶段 4 构建 Skill 时的**约束性输入**。各域已裁决部分维持原判，此处不重复。

## 一、数据引用与基调（对应 A1–A5、C4、D4）

1. **基调定为「质量依赖流程」**：既不乐观（Qodo 感知数据有幸存者偏差）也不悲观（社区实证投入流程可达人类水准以上）。Skill 的审查强度按 CodeRabbit 实测（AI 变更问题密度约 1.7 倍）设定「默认中高怀疑度」。
2. **实测优先于自述**：Skill 正文引用数据一律只采用带方法学的实测（GitClear、CodeRabbit、Veracode、METR、USENIX 幻觉包研究），且每处不超过一句、附方法学限定词（样本、场景）；自称/营销数据（Yegge 倍率、Anthropic 90%、YC 95%、Mnilax 41%→3%、vibecheck 31 仓库）**不进入 Skill 正文**，只留在研究档案。
3. **厂商报告降权**：引用时须带利益相关注记（如「安全厂商报告」）；Skill 正文尽量少引数据，把篇幅留给可操作规则。
4. **METR 与正收益研究**：按适用域并存，引用 METR 必须注明其工具代际与场景（资深开发者+大库+无 agent 工具）；Skill 正文不引用 METR（它是生产力数据，非质量数据）。
5. **GitHub 官方研究**：带 jadarma 方法学警示保留于研究档案；Skill 正文不引用。它的价值是提醒我们「引用数据前先做方法学检查」，这条原则本身写入 Skill 的评审文化。

## 二、护栏机制（对应 B1–B4、D2/D5）

6. **判断类规则的强制天花板**：采用「独立评审 agent + 四值判定」折中——判断类规则（命名、抽象、何时提问）无法 hook 化，其执行靠**独立上下文的评审者**用「符合/违反/未涉及/证据不足」四值判定（第四值防过度报告），再加**高频人审抽查点**。Skill 骨架即按此设计：执行流程（L5 指令）+ 独立评审（隔离上下文）+ 关键节点人审。
7. **AI 评审在环 vs 生成-评审分离**：按风险分级，但铁律不可妥协——
   - 铁律一：**评审者必须使用独立上下文**（新会话/子代理），绝不在生成者自己的会话里「自我评审」。
   - 铁律二：**测试与验证产物不可由被审代码的作者会话单方面修改/删除**（防篡改测试，Copilot 事故教训）；测试的增删须单独 diff 并说明理由。
   - 默认档：AI 先审（独立上下文、可跨模型）+ 人审关键路径；高危路径（认证、支付、数据访问、安全、并发）必须人审且逐行。
8. **SDD 定位**：默认轻流程 + 按风险升级。三档：小改动（直接做+验证门）、常规功能（简短方案确认+测试门+独立评审）、高风险/大改动（规格驱动全流程：规格→计划→任务→实现，每阶段有人工门）。简单任务不强制进重流程（superpowers 慢投诉教训）。
9. **宿主锁定**：Skill 正文写宿主无关的原理与流程；hooks/CI 配方以「附录示例」形式给出（Claude Code 语法 + 通用 pre-commit/CI 等价物各一份），并明确声明边界：「Skill 是请求，不是保证；确定性强制必须住在上下文之外」。不投入多宿主适配器工程。

## 三、方法论（对应 C1–C5、D1）

10. **抽象时机统一判据**（APSD vs YAGNI）：按「同一知识的三次真实重复」判——AI 语境下 Rule of Three 收紧执行：重复出现时先 grep 既有 helper 复用；确有三处且属同一知识才抽抽象；接口/热点路径（git log 高频变更区）允许提前设计接口；冷区宁可容忍重复。任何「为未来灵活性」的抽象推定有罪，需显式辩护。
11. **跨模型评审方向性**：写明「跨模型评审有效但方向敏感：有实验支持 Claude 审 Codex 方向（+18pp），反向为负收益；使用其他组合前先小样本验证方向；评审结论无论来源都必须人工抽查验证」。不写「多模型混审总是有效」。
12. **重构 vs 重写（regenerate, don't fix）**：分界判据 = 代码库的「存活特征」——已有真实用户/外部集成/测试存量/长期维护意图者，一律行为保持式重构（特征测试先行、小步、绞杀者模式）；纯原型（无用户、无集成、可整体丢弃）允许换提示词重生成，但须显式声明「这是原型，允许重写」。Skill 默认立场：被治理对象按「要长期维护」处理。
13. **评审深度分级（人审门槛）**：按「风险 × 可验证性」矩阵——高危路径（认证/支付/数据访问/安全/并发）逐行人审，无可妥协；中危（业务逻辑）AI 审 + 人抽样 + 测试证据链；低危（内部工具/原型/一次性脚本）半黑盒信任 + 事后检查 + 警惕「偏差正常化」（每次放过的小问题会抬高下次的默认底线）。可验证性高（测试覆盖充分、行为有金丝雀）可降一档。
14. **注释之争**：分层裁决维持（what 归代码结构、why 与接口契约必写、AI 生成注释须人复核）。TDD 分层裁决维持（正式代码 TDD 强制、原型转正以特征测试为门槛）。

## 四、工作流（对应 D3）

15. **过程纪律 vs 模型能力演进**：采用「骨架硬、血肉软」——硬门（验证证据、测试、评审分离、风险分级）写成具体流程，不随模型变强而放宽，因为它们防的是结构性风险；执行细节（怎么命名、怎么拆函数）写意图与判据而非死步骤，允许模型自主。Skill 颗粒度据此定：门禁具体、步骤适度抽象。
16. **规则治理投入产出**：规则文件由**人维护、AI 只能提议 diff**（中文社区「让 AI 治理规则文件效果差」的教训）；硬规则 ≤12 条、判断类常驻极简、其余索引化或 hook 化。Skill 自身不依赖「模型自觉遵守长清单」，而依赖流程门禁。
17. AI 代码质量目标定位：**通过流程稳定达到并保持「人类工程师可维护」水准**（可解释、可测试、可演进），不承诺「超越人类」，也不止步于「能用就行」。

## 五、Skill 工程形态（对应 E1–E6）

18. **架构**：单目录单主入口 + references/ 子技能文件（子 Skill 以独立 reference 文件承载，各有明确触发时刻与完整流程，主入口 SKILL.md 只做路由与不变量）。不拆成多个独立 skill（多 description 常驻成本高、触发分裂）。
19. **语言**：**全中文**（正文、description、标题全部中文；代码标识符、hook/CI/DRY/YAGNI/diff/token 等技术名词可保留英文原词，但不得出现英文句子）。description 用中文场景词密集覆盖触发场景（重构、清理、审查、简化、优化、坏味道、AI 生成代码……）。
20. **脚本**：附最小 stdlib Python 证据收集器（1 个主脚本，零第三方依赖，输出 JSON 证据：长函数、深嵌套、重复块、残留标记等），定位「证据收集器，不是裁判」。附最小自测。
21. **重复度**：红线/关键不变量在主入口与子文件中重复 ≤2 处且措辞不同。
22. **主入口规模**：SKILL.md 目标 100–150 行（硬上限 500 行）；每个子技能文件 60–120 行；引用链一层深。
23. **不建独立触发 eval 集**；description 按 should/should-not 原则自查，由阶段 5 审查 agent 做触发词覆盖检查。
24. **反照抄**：所有内容派 subagent 基于整合知识重新组织、改写、再创作；严禁整段搬运源材料（专有名词与代码示例除外，代码示例须自造）。

## 六、裁决后的一致立场（Skill 的世界观，供构建时统一措辞）

- AI 生成的代码默认「能用但不可维护倾向高」：膨胀、重复、过度防御、过度分层、测试薄弱。治理目标是可维护性，不是炫技式净化。
- 治理靠三层：**流程门**（验证证据、测试、评审分离）> **独立评审**（隔离上下文、四值判定）> **规则文本**（少而硬、常驻极简）。
- 人始终保留：风险分级裁决、高危路径逐行审、规则文件的最终维护权。
- Skill 对自身诚实：声明「本 Skill 是提示层约束，无法保证遵守；确定性强制请配置 hooks/CI（见护栏子技能示例）」。
