# 质量优先的协作工作流：从需求到收尾

> 何时读我：接到任何编码任务、准备动手之前——第一件事是分级，不是写码；执行到一半冒出「上下文快满了」「方案好像不对劲」「这好像不归我改」的直觉时；准备宣称「做完了」之前——收尾动作在这里，不在别处。本文件只管全程怎么走；评审细则与四值判定见 `references/review.md`。

## 一、第一步永远是分级，不是写码

流程是成本，防的是风险；档位与风险对齐才不亏。用三个判据定档：

| 判据 | 问自己 |
|---|---|
| 影响面 | 波及几个模块？有没有外部调用方、数据格式、接口被牵连？ |
| 风险路径 | 是否触碰认证、支付、数据访问、安全、并发？ |
| 核心程度 | 是否改动核心数据结构、公共契约、架构边界？ |

三档流程：

- **T1 小改动**：影响面锁在单模块、不碰风险路径、不动核心（例：修文案、调样式、补一个纯函数）。直接做，但验证门不豁免——改完必须跑检查并出示新鲜证据。
- **T2 常规功能**：新增局部功能或有限重构，跨多个文件但不改公共契约。流程：简短方案确认 → 测试门 → 独立评审。测试门的通过判据：新增与变更的行为都有对应测试，且这些测试至少红过一次（证明真能拦住回归）；全量测试与 lint 无新增失败；关键路径人工冒烟一遍通过。
- **T3 高风险大改动**：触碰风险路径、动核心契约、或删改存量行为。流程：规格驱动——规格 → 计划 → 任务 → 实现，每个阶段过一道人工门才准进下一个。

禁止两个极端：把 T3 伪装成「帮我顺手改一下」直接开工；把 T1 拖进全套规格流程（10 分钟的事跑 1 小时流程，流程税会反过来诱使人放弃流程本身）。

拿不准档位时往上调一档，并把定档结论连同理由报给人——定档是人的裁决权，AI 只提案。注意伪装成小改动的 T3：一句「帮我把这个校验放宽一点」，牵动的可能是数据完整性边界；判断看的不是改动行数，是改动站在什么位置上。

分级不是一次性的。执行中发现实际影响面比定档时更大（例如小改触到了公共契约），立即升档并补走对应流程，不要沿用旧档位的豁免。

## 二、需求澄清门：不懂就问，但问得克制

AI 最危险的失败不是写出坏代码，而是安静地填了一个错误假设——代码能跑、测试全绿、方向从第一行就错。应对：

- **先重述再动手**：用自己的话复述目标与边界，请人确认。复述暴露偏差的成本是一句话，暴露在成品上的成本是整个返工。
- **提问设上限**：最多 3 个最关键的问题，按「影响范围 > 安全 > 行为细节」排序。能查代码确认的事实不问人；可用行业惯例的先采用并声明；问满 3 个仍卡住，说明该先做调研而不是继续追问。
- **声明假设而非默默假设**：每个不得已的默认选择写进方案的「假设」清单——让人一眼看到你替他做了哪些决定，他才有机会否决。
- **主动索要意图**：请用户补一句「我想解决的问题是 X」。一句意图说明能让表面需求背后的真实约束浮出水面；只描述症状不给意图，AI 就会不停道歉然后接着犯同一个错。

提问质量的对照（自造示例）：

- 坏问题：「错误处理要怎么做？」——把整块决定扔回给人，人会觉得你在推卸思考。
- 好问题：「失败时用户应看到原样页面还是空态提示？我倾向空态并记日志，因为原样页面会让用户误以为数据为空。」——给出带理由的倾向，人只需确认或否决。

## 三、方案确认：锁决定层，放实现层

方案的价值在于锁住「AI 独自做不对的决定」，不是替实现抢跑。计划写太细有两个恶果：过度指定剥夺模型的工程判断；计划膨胀成第二份实现，从此维护两份代码。

一份合格的方案（T2 简版、T3 全版）由五件套组成：

1. **为什么做**：一两句意图，执行遇歧义时它是仲裁依据。
2. **动哪些文件**：确切路径清单；清单外的文件一个不碰。
3. **契约签名**：新增或修改的函数签名、类型形状、接口定义。
4. **验收标准**：每条必须是可执行的检查——「跑哪条命令、断言什么输出」，而非「日志模块更完善」。它防的是「绿而不对」：测试完全可能被做到全绿，做的却不是方案说好的事；所以收尾核验要双对照——先核方案意图有没有达成，再看测试是否全绿，只看后者等于没验。
5. **约束**：行为保持类任务注明「先补特征测试再动手」、依赖增禁、错误处理策略等项目级规则。

留在实现层自由发挥的：函数体、内部步骤序列、测试代码细节。只在真正的难点（并发时序、状态机边界、绕不开的算法）处给伪代码，并标注「示意，允许更优实现」。

验收标准对照（自造示例）：

- 意图陈述（不合格）：「重试逻辑更健壮。」——无法证伪，任何人都能宣布它完成。
- 可执行检查（合格）：「构造一次 503 响应，断言客户端重试 2 次后成功，且每次间隔 ≥500ms。」——跑一条命令就能得到是或否。

## 四、执行纪律：小步、台账、四个停机条件

- **小步走**：一步只做一件事，收口交给裁判——开工前一句话讲清这一步要什么，改完立刻跑秒级检查（类型检查、lint、相关测试），不绿不进下一步。出红先恢复原状，再把这一步切得更小重来，不许在原地摞补丁；同一处连红 3 次即停手——错的大概率在方案或规则，不在手气，硬撞只会越撞越歪。
- **测试先行分层**：定价、权限、认证、计费这类正式代码的关键逻辑按测试先行推进——先写会失败的测试，再写实现；原型代码允许事后补测，但转正前必须补齐特征测试。
- **上下文外置，建执行台账**：把「改动清单 / 已验证项（附证据）/ 待办」写进一个 markdown 文件，每完成一步就更新。为什么：会话压缩会丢计划状态、降权项目指令，而台账活在上下文之外，压缩打不掉它。恢复工作 = 重读台账 + 对账 git log，绝不是「回忆一下刚才做到哪」。台账条目示例：`[x] cache.ts 缓存替换为 LRU — 已跑 cache.test.ts 全绿（12/12）`——一行里同时有事实和证据。
- **四个停机条件**——触发任何一条立即停，带着问题清单回来，绝不悄悄绕过：
  1. 需求变了：执行中发现任务目标与用户最新表述冲突；
  2. 方案错了：证据表明计划本身有误，继续只会放大错误；
  3. 超出声明范围：必须改方案没列的文件，或执行不可逆、破坏性操作；
  4. 需要人裁决：遇到方案未覆盖、且影响行为或契约的岔路口。

  停机清单的格式：现象 / 我倾向的选项与理由 / 不停手的代价。带病续跑永远比重新开始贵。

## 五、评审与收尾

- **独立评审**：T2/T3 完成后，用独立上下文（新会话或子代理）评审本次 diff——评审者的输入 = 变更 diff + 方案中的意图与约束（或等价的意图说明），绝不含生成者的会话历史。评审方法、四值判定、证据分级见 `references/review.md`。高危路径（认证、支付、数据、安全、并发）交人逐行审，不可代理。
- **规则沉淀走 diff**：本轮踩的坑若具「下次还会犯」的性质，提炼成一条规则，以 diff 提议交给维护规则文件的人。AI 不直接改规则文件——规则的最终维护权在人。
- **清理生成残留**：删除临时调试代码、注释掉的旧实现、撒谎的 TODO、本轮产生但已过时的文档段落。文档只记录现状，不记录历史思潮。删除前先读——确认删的确实是残留，而不是他人正在依赖的东西。
- **收尾报告四件套**：改了什么 / 如何验证（附证据）/ 剩余风险 / 显式 TODO。查过什么就报什么，没查的部分直说没查——总结读起来越漂亮，越要警惕它替你补了你没做的事。

## 六、上下文与会话管理速查

- 会话该不该收尾看信号，不看占用比例：开始重复提问、重读已经读过的文件、忘记早先确认过的约束——任一出现就收尾当前会话。瓶颈不是窗口容量，是塞满之后召回质量先崩，硬撑没有收益。
- 长任务换新会话时用「索引 + 正文」两层记忆交接：索引层一段话讲清任务状态与文件入口，正文层就是执行台账。新会话先读索引，再按需读正文。
- 交接时继承已取得的验证证据（哪些测试已跑绿、在哪个 commit），不要让新会话从零重跑全套——重复劳动之外，更会丢失「哪些结论是验证过的、哪些只是猜测」这条边界。
- 文件整洁度是输出天花板：60 分的文件只会得到 60 分的产出，与模型能力无关。感觉产出质量下滑时，先清理再继续——死代码与过时文档在污染每一次后续生成。
- 同一会话里纠偏超过两轮仍不见效，换新会话重来；在旧会话里继续拉扯，错误会越叠越深。

## 七、多任务并行

- 实现类工作并行度保持 ≤2：多一个并行实现，token 成本翻数倍，编排开销会吃掉全部收益。
- 只有机械批量变更（同一模式改 N 个文件）才 fan-out 给子代理，且只带回结论与证据，不带回过程叙述。
- 派出的子代理不共享你的上下文：给它的指令必须自包含——读哪个文件、按什么标准判——否则它只会带着猜测回来。
- 评审者永远用独立上下文（红线，见主入口），细则见 `references/review.md`。
- 规划留在单会话深上下文里完成：拆开会丢全局一致性，而一致性恰恰是规划期最贵的东西。

## 单任务生命周期速查表

| 阶段 | 门 | 通过条件 | 产物 |
|---|---|---|---|
| 分级 | — | 三判据（影响面 / 风险路径 / 核心程度）定档 | 档位结论 T1/T2/T3 |
| 需求澄清 | 澄清门 | 重述获确认；提问最多 3 个；假设已声明 | 任务口径 + 假设清单 |
| 方案（T2/T3） | 方案门 | 五件套齐全、验收可执行、人点头 | 方案文档 |
| 规格驱动（T3） | 人工门 | 规格、计划、任务分解逐段获批 | 规格 + 任务列表 |
| 执行 | 验证门 | 每步有新鲜验证证据；台账同步；无停机条件触发 | 代码 + 执行台账 |
| 评审 | 评审门 | 独立评审通过；高危路径人审完成 | 四值判定评审结论 |
| 收尾 | 收尾门 | 残留已清、删除项均已先读、规则 diff 已提议 | 干净 diff + 含证据与剩余风险的报告 |
