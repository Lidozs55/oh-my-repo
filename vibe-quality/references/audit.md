# 代码质量审计：体检流程

> 何时读我：拿到一块既有代码（多为 AI 生成或 AI 深度参与），需要产出一份带证据的问题清单时读本文。审计是体检不是治疗——只定位、只分级、只给证据，不改一行代码；修什么、怎么修由人或后续修复流程决定。

## 一、审计在治理结构里的位置

三层治理（流程门 > 独立评审 > 规则文本）中，本流程属于独立评审层：站在生成流程之外看代码，把结论交还给流程门与人。独立性靠执行方式兑现：另开干净上下文做审计，只带文件清单进来，不在生成代码的会话里顺手自查（红线，见主入口）。

## 二、审计前定位（两件必须先做的事）

### 判存活特征

先回答「这块代码按什么对象处理」，因为后续所有结论的口径都取决于它：

- 查三样存量：真实用户或调用方、外部集成（数据库、支付、第三方 API）、测试。
- 任一存在 → 按长期维护对象审计，结论面向行为保持式重构；此时测试缺口足以单独立案（后续以特征测试补保护网）。
- 三样全无、整体可丢弃 → 这是原型：审计只需回答「留不留」，换提示词整体重生成也是合法选项，但报告必须写明「原型，允许重写」。
- 拿不准 → 一律按长期维护处理，这是默认立场；分级细则与处置路线见 `references/simplify.md` 的前置门，本文只做审计侧的最小判定。

### 划范围

- 列出文件清单（精确到路径），展示给使用者确认后再动手。
- 要扫全库时先给理由与成本预警。没有边界的审计必然失焦：AI 代码的膨胀与重复几乎无处不在，全开火力得到的清单什么都像问题、什么都不具体。
- 范围外被牵连的文件（被审模块的调用方等）记入「关联文件」单独标注，不混入主清单。

## 三、三级证据收集（顺序不可倒置）

总原则：机器能数的不用人眼，人眼看的必须落到行，落不到行的只能叫估算。前一级的输出是后一级的输入。

### 机械层：工具先跑

- 先跑 `scripts/quality_scan.py`（九类检查：长文件、长函数、深嵌套、重复块、残留标记、调试残留、空捕获、超长行、解析失败），再跑项目自带 lint 与针对性 grep。
- 证据 = 工具输出本身。报告引用的每个数字（行数、深度、重复块位置）都必须能回溯到一条真实执行的命令；没跑过的命令不产生数字。
- 记住脚本定位：它是证据收集器，不是裁判。它圈出的是「值得看一眼」的可疑点，不是「已经违规」的结论——是否构成坏味道，交给语义层与坏味道目录判。
- 工具缺失或跑不动，就在报告里写明缺什么、影响哪些指标，不许拿想象补位。

### 语义层：抽样深读

- 动眼之前先花 10 分钟画一张最小项目地图：入口在哪、数据怎么流、依赖指向谁。画不出地图就先记下这条问题——比如被问「这笔钱从哪条链路扣、记到哪本账」时张口结舌，说明该区域没人真正理解，深查优先级随之抬高。
- 按风险排序选读：入口文件、安全与资金路径、高频改动的热点优先，冷区降频。
- 读的目标是判断意图与实现是否错位：逻辑对不对、命名是否名实相符、抽象是服务当前需求还是服务想象中的未来。
- 铁律：每条语义结论必须落到具体文件与行号。给不出位置的不是发现，是印象。
- 抽样必须如实交代覆盖度：读了哪些、跳过哪些，明说。让读者误以为全查过，比少查更糟。

### 估算层：诚实降级

- 工具测不了、读代码也确认不了的判断（如重复程度的大致量级），只能标「估算」。
- 绝不把估算包装成机械证据，绝不编造百分比与数字。读者一旦发现一个假数字，整份报告的结论都会被连带怀疑——这是审计信用的死刑。
- 宁可写「未测：缺少克隆检测工具」，也不给一个看起来精确的数。

## 四、与坏味道目录联动

- 机械层与语义层定位出的可疑点，对照 `references/smells.md` 逐类深查对号：是长函数还是上帝类、是重复知识还是偶然相似。
- 归类的价值一半在确认、一半在排除误报：目录为每类坏味道写了判据与例外，生成代码、协议强制的嵌套不该被误报成病灶。
- 目录没覆盖的新型问题归入「未分类」交人判断，不硬塞进相近类别制造假精确。

## 五、四值判定：每条发现必标其一

- **符合**：查过且达标。写下来——让人知道这块查过、没病，与查出病同等重要。
- **违反**：证据充分成立。只有这一类进入修复决策。
- **未涉及**：本次范围没碰到。如实标注，不装作查过。
- **证据不足**：有怀疑但拿不到证据。这是合法结论，不是审计失败。

为什么必须有后两值：检查类流程最典型的垮法不是漏报而是滥报——十条里九条靠猜，读者读到第三条就弃读整份清单，真问题随之陪葬。拿不准就写「证据不足」，把裁量权交还给人。

## 六、风险分级与报告

- 高危单列置顶：涉及安全（注入、密钥、越权）、数据（丢失、损坏、迁移）、资金（计费、支付）、并发（竞态、死锁）的发现，无论证据来自哪层，一律放报告最前独立成节。代价不对称：漏掉一个高危的损失，远大于多审十处低危。
- 其余按中危（业务逻辑、契约一致性）、低危（命名、死代码、风格）排序。注意：本文件的高/中/低危指单条发现的影响档；按风险定审阅深度的那套分级见 `references/review.md`。
- 每条按「审计发现格式」写四栏：位置（文件:行）、问题（一句话说清）、证据（标 机械/语义/估算 + 来源）、建议（指路不代修）。

条目示例（自造）：

```
[中危·违反] 同一条折扣规则在两处各写一份
- 位置：src/pricing/cart.py:88、src/pricing/coupon.py:31
- 问题：同一业务规则存在两份平行实现，改一处漏一处
- 证据：机械——重复块扫描命中；语义——读两处源码，确认编码同一条规则
- 建议：提取为单一规则函数，两处调用；改前先给现有行为补特征测试
```

## 七、审计纪律（不变量）

- 只产出清单与证据，不改代码。审计一旦动手修，独立性即刻归零，清单也从证据退化成自辩。
- 无证据不下结论；每条发现都能自证：谁查的、用什么查的、查到了什么。
- 覆盖度如实声明：跑了什么命令、读了什么文件、跳过了什么。
- 根因段要克制：先亮「推断」标记，再谈内容。每条假设必须挂靠清单里已出现的编号，不许凭空引入新问题；数量以三条封顶。假设对不对，等修复后回头再扫一遍才算数——文字推得再漂亮也不加分。

## 八、报告最小结构

```
# 质量审计报告：<模块或范围名>
1. 定位：文件清单 + 存活特征判定（按长期维护 / 原型）
2. 高危发现：单列置顶；没有就写「无」，不许留空
3. 其他发现：按风险排序，每条四值判定 + 审计发现格式
4. 覆盖度声明：工具与命令清单、已读 / 跳过的文件
5. 根因假设：最多三条，逐条标注推断，留待修复后复扫检验
```
